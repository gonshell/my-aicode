# 实体定义 QA 补全方法论（stage9）

## 核心原则

1. **先审计覆盖缺口，再补**——很多术语只是"被提及"，从未被定义
2. **宁缺毋滥**——质量优先，不硬凑数量
3. **规则 > LLM**——模板化输出直接规则提取，LLM 只增加失败面

## 覆盖缺口审计（三层递进）

| 层 | 检查 | 说明 |
|----|------|------|
| L1 | 术语被提及过吗？ | 答案中出现过该词 |
| L2 | 有定义类问答吗？ | 问题匹配"是什么/定义/含义"等宽松模式 |
| L3 | 有独立定义条吗？ | 问题核心就是问"XX是什么"（`{t}是什么？`/`什么是{t}？`） |

通常 L3 独立定义覆盖率远低于 L2（实测 25% vs 93%）——"滤板的作用是什么"不等于"滤板是什么"。

## 实体分类与提取难度

| 实体类型 | 提取方法 | 成功率 | 注意事项 |
|----------|---------|--------|----------|
| 故障代码 | 规则提取 | 高 | **必须设备绑定**——同一代码不同设备含义不同 |
| 标准编号 | 规则提取 | 中高 | 从"相关标准"列表项提取名称重组 |
| 润滑油牌号 | 规则提取 | 中高 | 只留类型，删用量/配比等使用细节 |
| 部件术语 | 规则噪声大 | 低 | 自动组装语法不通，需人工终审 |
| 工艺术语 | 规则噪声大 | 低 | 同上 |
| 设备型号含义 | 部分可提取 | 低 | 有"XX代表YY"格式的才能准确定义 |

## 故障代码：设备绑定是硬约束

**典型陷阱**：F01 在多设备中含义完全不同，通用定义 = 事实错误。

正确做法：
1. 按 `(代码, 设备)` 二元组分组，暴露多设备歧义
2. 每（代码×设备）生成一条：`在{设备名}中，{代码}表示{含义}。`
3. 即使单设备独有，答案也带设备限定

**提取模式**：`F\d{2}-含义` / `E\d{2}代表"含义"故障` 等。先 grep 真实样例再写正则，不要凭空想格式。

**正则后清理三类残留**：
1. 半边引号 → 去引号
2. 截断的设备名 → 补全或用文档名
3. 含义+多余词非连续组合 → 回退到原文连续片段

## 标准编号定义格式

`{标准号}是《{标准名称}》的{类别}标准编号。`

类别判断（按前缀）：
- GB → 国家标准
- JB → 机械行业标准
- MT → 煤炭行业标准
- DL → 电力行业标准
- HJ → 环保行业标准
- ISO → 国际标准

提取不到名称的舍弃。

## 润滑油牌号定义格式

`{牌号}是{油品类型}。`

只保留类型（如"抗磨液压油""工业闭式齿轮油"），删除用量、配比、添加剂等使用细节。

## 规则提取定义句的清洗规则

自动提取的定义句噪声极大，需多层过滤：

1. 答案必须以术语开头（术语+是/为/指/：）
2. 术语后不能紧跟动词（检查/确认/更换/处理…）→ 操作句非定义
3. 排除编号列表项
4. 排除纯参数值（术语后仅数字+单位）
5. 长度 8-150 字

**典型失效模式**：
- 句子片段被当术语（"先关闭XX打开YY是"）
- 术语后截取描述产生语法残句（"滤布是应根据物料性质选择：1.…"）

存活率约 30% 是正常的，剩多少用多少。

## 合并约束

新增定义条目合并时，如用户要求 test 集条数不变：
- 新增条目 group_id 用固定前缀（如 `def_fault_{code}`）
- 按"test 已有 group_id 集合"重切，新组全部落 train

## 质量红线

- 核心事实必须可回溯原文
- 通用化定义（跨实体共享）= 事实错误，宁可不做
