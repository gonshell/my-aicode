# Model Deep Dive — 开源模型深度分析

> 给定 HuggingFace / ModelScope / GitHub 链接，输出结构化的深度技术分析报告。
> 核心价值：信息采集自动化 + 分析框架化 + 判断有标注，保证深度和一致性。
>
> 2026-09 实测验证：Qwable-v1 三级蒸馏链路分析、Qwen3.5 生态四模型横向对比。

## When to use

- 用户说"分析一下这个 HF 模型 / ModelScope 模型 / GitHub 项目"
- 用户说"对比这几个模型"
- 技术调研、模型选型参考
- 任何需要"吃透一个开源模型项目"的场景

## 不做什么

- 不跑 benchmark 实测（那是 lm-eval / vLLM 等工具的事）
- 不预测未来发展
- 不写训练代码（那是微调训练类技能的事，如 `qwen-dual-mode-lora-training`）
- 不凑字数：信息不足就明说，不编造

## 调用约定

自然语言触发，参数约定如下：

```
model-deep-dive <url1> [url2] [url3] ... [选项]
```

| 选项 | 默认值 | 说明 |
|---|---|---|
| `--depth full/brief` | `full` | 简报（4 模块）vs 完整分析（7 模块） |
| `--compare` | 自动 | 多模型时输出横向对比（≥2 个自动开启） |
| `--output-dir <path>` | `./model-reports` | 输出目录 |
| `--format md/html/both` | `both` | 输出格式 |

支持的 URL 类型：

| 类型 | URL 模式 |
|---|---|
| HuggingFace 模型 | `huggingface.co/{org}/{model}` |
| HuggingFace 数据集 | `huggingface.co/datasets/{org}/{name}` |
| ModelScope 模型 | `modelscope.cn/models/{org}/{model}` |
| GitHub 项目 | `github.com/{org}/{repo}` |

## 输出文件

单模型：
```
{模型名}_深度分析.md
{模型名}_深度分析.html
```

多模型（N 个）：
```
model1_深度分析.md / .html
model2_深度分析.md / .html
...
横向对比.md / .html       （≥2 个时自动生成）
```

## 核心原则

### 追到底座和数据源（硬约束）

分析蒸馏/微调模型，只读顶层模型卡是远远不够的——必须沿 `base_model` 和 `datasets` 字段逐级向上追：

1. 顶层模型（学了什么行为/格式）
2. 中间蒸馏模型 + 它的教师与数据集卡（推理/能力从哪来）
3. 底座模型（架构参数、原生能力上限）

每一级都拉 README 交叉验证。用户明确要求过：不深入底座和数据源的分析"不算足够深入的研究"。关键判断（如"能力 99% 来自底座"）只有追完链路才成立。

### 事实 / 分析 / 判断 三级标注

报告中所有内容必须标注级别，让读者知道什么是硬事实、什么是推断：

| 级别 | 标记 | 含义 | 占比目标 |
|---|---|---|---|
| **事实** | 无标记（默认） | 直接从公开资料提取的信息，可溯源 | ~60% |
| **分析** | ⚠️ 分析 | 基于事实的推理、归纳、对比 | ~25% |
| **判断** | 💡 判断 | 带有主观倾向的结论、评价、建议 | ~15% |

断言强度 ≤ 证据强度。效果平平就写平平，不用"惊艳""颠覆"类词。

### 信息源分级

不是所有信息可信度一样。按等级排列，高等级优先引用：

| 等级 | 来源 | 可信度 |
|---|---|---|
| S | 官方模型卡 / 论文 / 官方文档 | 最高 |
| A | 作者 GitHub README / 代码 / 配置文件 | 高 |
| B | 关联数据集卡 / 姊妹项目文档 | 中高 |
| C | 第三方博客 / 评测 / 社区讨论 | 中 |
| D | 社交媒体 / 传言 | 低，仅作背景参考，不当事实引用 |

所有数字标注来源；作者发布未经验证的结果要写明"未独立验证"。

### 数字交叉验证（硬约束）

训练步数 = 样本数 × epochs ÷ 有效 batch，能对上的才算采信；对不上的在报告中指出。
README 说"10K 数据"但数据集卡说"5K"，要查清楚并标注差异。

### 深度 = 信息量 / 字数

追求信息密度，不是字数。同样的信息，能用表格说清就不用段落。
判断是否"足够深"的标准：读者看完报告，能不能回答——

1. 这个模型/项目到底做了什么？（一句话能说清）
2. 怎么做到的？（方法 + 配置 + 数据）
3. 效果怎么样？（量化指标 + 和同类比）
4. 为什么这么设计？（关键选择的理由）
5. 有什么代价？（trade-off + 局限性）
6. 适合/不适合什么场景？（定位边界）

## 分析框架（7 模块）

### Module 1：项目定位

- 项目/模型名、作者、许可协议、发布时间
- 一句话定位：解决什么问题
- 底座模型是什么（追到底座）
- 在生态中的位置（和同类的关系）

### Module 2：训练配置

必查清单（10 项）：

- [ ] 底座模型是什么？为什么选这个底座？
- [ ] 训练方法（SFT/DPO/RL/全量/QLoRA/LoRA）
- [ ] LoRA 配置（rank/alpha/target_modules/dropout）
- [ ] 超参数（lr/batch/epochs/optimizer/scheduler/warmup）
- [ ] 序列长度
- [ ] loss 掩码策略（response-only / full）
- [ ] 硬件配置（GPU 型号/数量/显存）
- [ ] 训练时间和成本估算
- [ ] 训练工具/库（Unsloth/TRL/axolotl/LlamaFactory 等）
- [ ] 最终 loss / 收敛情况

缺失就标记"未公开"，不猜。

### Module 3：数据

必查清单（8 项）：

- [ ] 数据集名称和来源
- [ ] 数据量（条数 / token 数 / 时长）
- [ ] 数据领域 / 任务类型分布
- [ ] 数据处理流程（筛选条件 / 清洗 / 格式化 / 增强）
- [ ] 数据质量控制机制
- [ ] 教师模型（如果是蒸馏）— 用谁的知识、怎么蒸馏的
- [ ] 数据是否公开可复现
- [ ] 数据的已知问题 / 局限性

⚠️ 分析：数据质量 vs 数据量的取舍，数据筛选策略的影响。

### Module 4：评估结果

必查清单（6 项）：

- [ ] 测了哪些 benchmark？覆盖哪些能力维度？
- [ ] 基线是谁（底座 / 同类 / SOTA）？
- [ ] 各项指标提升/下降了多少？
- [ ] 评估方法（框架 / 配置 / 评估者）
- [ ] 有没有选择性报告（只报涨的不报跌的）？
- [ ] 评估结果和训练目标一致吗？

输出格式：基准成绩表 + 变化量标注。
⚠️ 分析：哪些提升是真实的，哪些可能是评估方法本身的问题。

### Module 5：技术设计分析

这是深度的核心。不是复述配置，而是回答"为什么"。

必查清单（5 项）：

- [ ] **关键设计选择**：这个项目最与众不同的 2-3 个设计决策是什么？
- [ ] **设计理由**：作者为什么这么选？（从文档/代码/issue 中找依据）
- [ ] **Trade-off**：这个设计换来了什么，付出了什么代价？
- [ ] **工程坑**：作者踩过哪些坑，怎么解决的？
- [ ] **适用边界**：这个方法在什么条件下有效，什么条件下可能失效？

💡 判断：和同类项目比，这个设计选择是聪明的、常规的、还是有问题的？

### Module 6：局限性 & 风险

分层呈现：

1. **作者自述的局限** — 直接引用
2. **⚠️ 补充分析的局限** — 基于分析的推断
3. **💡 潜在风险** — 更长期的担忧

覆盖维度：
- 技术局限性（能力边界、泛化性）
- 数据局限性（分布、质量、偏见）
- 可复现性（数据/代码/配置是否完整）
- 许可风险（商用限制、数据合规）

### Module 7：定位 & 价值

最后给一个明确的结论：

- 这个项目的**核心贡献**是什么（一句话）
- **适合**什么场景 / 什么人用
- **不适合**什么场景
- **技术参考价值**（高/中/低 + 理由）
- 💡 判断：在同类方案中的相对位置（Top 梯队 / 中上 / 普通 / 不推荐）

### Brief 模式

`--depth brief` 时只输出 Module 1/2/4/7（定位 / 配置 / 评估 / 结论），跳过数据细节和深度设计分析。

## 多模型横向对比

输入 ≥ 2 个项目时，额外生成一份横向对比报告。

### 对比维度（统一标尺）

| 维度 | 说明 |
|---|---|
| 定位 | 各自解决什么问题 |
| 底座 + 方法 | 技术路线对比 |
| 数据量 + 质量 | 数据规模和筛选严格度 |
| 训练成本 | 时间 / 硬件 / 金钱估算 |
| 效果 | 同一 benchmark 上的表现（能对齐的就对齐） |
| 工程质量 | 文档完整度 / 代码质量 / 可复现性 |
| 局限性 | 各自的短板 |
| 适用场景 | 什么情况选哪个 |

💡 判断：给出选型建议——不同需求下推荐哪个，为什么。

## 信息采集（自动化脚本）

用 `scripts/fetch_model_info.py` 自动采集公开资料。零依赖（标准库 urllib）。

支持的数据源：

| 源 | 采集内容 |
|---|---|
| HuggingFace 模型 | README + API 元信息 + 文件列表 + 关联数据集 + 关联底座 |
| HuggingFace 数据集 | README + API 元信息 + 字段说明 |
| ModelScope 模型 | README + 元信息 + 文件列表 |
| GitHub 项目 | README + 文件树 + 自动识别关键脚本（train/finetune/config/lora 等） |

采集输出结构：
```
{model_id}/
├── README.md           # 原始 README
├── meta.json           # API 返回的元信息
├── files.json          # 文件列表
├── related_datasets.json # 关联数据集（如果有）
├── src_*.py            # GitHub 关键脚本（自动识别下载）
└── source.txt          # 来源 URL + 类型
```

> 注意：HF 的 `web_extract` 常被 URL 策略拦截，直接用 urllib 打 API/raw 端点更稳定。

## 工作流

```
1. 解析输入
   ├─ 识别 URL 类型（HF / ModelScope / GitHub）
   └─ 判断单模型 / 多模型

2. 信息采集（脚本自动化）
   ├─ 拉顶层模型 README + 元信息
   ├─ 沿 base_model 向上追底座（硬约束）
   ├─ 沿 datasets 追数据集卡（硬约束）
   └─ GitHub 项目拉 README + 关键脚本

3. 信息提取（LLM 主导，脚本辅助）
   ├─ 提取训练配置表
   ├─ 提取数据表
   ├─ 提取评估结果表
   └─ 交叉验证数字（不同来源同一数字是否一致）

4. 深度分析（LLM 核心价值）
   ├─ 按 7 模块框架展开
   ├─ 每个分析/判断标注级别（⚠️ / 💡）
   ├─ 找 trade-off 和设计理由
   └─ 评估局限性和适用边界

5. 生成报告
   ├─ 按模板输出 md
   ├─ 转 HTML（调用 md-to-styled-html）
   └─ 多模型 → 加横向对比

6. 质量自检
   ├─ 7 模块都覆盖了吗？（brief 模式除外）
   ├─ 底座和数据源追了吗？（硬约束）
   ├─ 事实/分析/判断标注了吗？
   ├─ 数字交叉验证了吗？
   └─ 信息不足的地方有没有明说？
```

## 配置

默认配置在 `config.json`，优先级：
**调用参数 > 环境变量 > 技能目录 config.json > 默认值**

| 配置项 | 默认值 | 环境变量 | 说明 |
|---|---|---|---|
| `depth` | `full` | `MDD_DEPTH` | `brief` 或 `full` |
| `output_format` | `both` | `MDD_OUTPUT_FORMAT` | `md` / `html` / `both` |
| `output_dir` | `./model-reports` | `MDD_OUTPUT_DIR` | 输出目录 |
| `html_theme` | `tech-dark` | `MDD_HTML_THEME` | HTML 主题 |
| `include_comparison` | `auto` | `MDD_COMPARE` | 多模型时是否生成横向对比 |
| `fact_annotation` | `true` | `MDD_FACT_ANNOTATION` | 是否标注事实/分析/判断分级 |

## 质量检查清单（交付前必过）

- [ ] 底座和数据源都追了（至少追到上一级）
- [ ] 一句话定位清晰准确
- [ ] 训练配置 10 项都查了（缺失标"未公开"）
- [ ] 数据 8 项都查了
- [ ] 评估结果有基线对比，不是孤立数字
- [ ] 至少找到 2-3 个关键设计选择并分析了理由
- [ ] 局限性分了三层（作者自述 / 补充分析 / 潜在风险）
- [ ] 所有分析/判断都有标注（⚠️ / 💡）
- [ ] 数字做了交叉验证，不一致的地方有说明
- [ ] 信息不足的地方明说了，没有硬凑
- [ ] 文末有明确的定位结论和适用场景
- [ ] HTML 渲染正常（TOC / 表格 / 代码块）
- [ ] 报告末尾注明"基于公开信息，非实测验证"

├── config.json               # 默认配置

## Pitfalls

1. **只读顶层模型卡**：蒸馏/微调模型的能力 99% 来自底座，不追到底座等于没分析。硬约束：必须沿 base_model 向上追。
2. **把作者说的当事实**：作者在 README 里的 claim 需要和评估结果交叉验证。作者说"提升了 X%"，要看 benchmark 数据支不支持。
3. **只看正面结果**：很多项目只报涨的不报跌的。要主动找"降了什么"——GPQA 降了、IFEval 降了、代码能力降了，这些才是理解 trade-off 的关键。
4. **数字不交叉验证**：README 说"10K 数据"，数据集卡说"5K"，要查清楚。常见不一致：数据量、训练时间、参数量。
5. **过度推断**：从有限信息推出太具体的结论。比如"用了 LoRA rank=64 说明数据量大"——这不一定。标注为💡判断，不是事实。
6. **忽略许可**：很多模型可以玩但不能商用。MIT / Apache 2.0 / AGPL / 自定义许可，差别很大。必须查。
7. **GitHub 项目只看 README**：配置文件（config.yaml / train.sh / requirements.txt）里的信息往往比 README 更准确。README 可能过时，配置文件不会。
8. **README 404**：`resolve/main` 失败换 `raw/main`；模型卡可能只有 frontmatter+短文，信息以数据集卡补充。
9. **GitHub 分支名**：raw 链接的分支名（master/main）逐仓确认。
10. **f-string 反斜杠**：转换/解析脚本不要在 execute_code 里内联——先 write_file 落盘再 terminal 跑（详见 md-to-styled-html Pitfall #8）。
