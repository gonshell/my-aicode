## 零、Token 效率（全体系通用，最高优先级）

**原则：上下文是稀缺资源。流程已脚本化的任务，模型只做"判断/生成"，机械处理全走脚本。**

### 0.1 禁止临时代码
- 技能已提供 `scripts/` 脚本的流程，**必须调用脚本**，禁止在会话里重写提取/切块/回填/渲染逻辑
- 每次重写 = 每任务浪费 30%+ token（读 HTML 噪音 + 写调试脚本）
- 发现流程没脚本化 → 报告并沉淀脚本，不要每次手工做

### 0.2 模型上下文只进"必要内容"
- 大文件（>1MB，含图片 base64）**禁止整读进上下文**：先 `search_files` 定位，再用 `read_file` 分页，或脚本先切块/统计再输出紧凑摘要
- 只读待处理的文本本身，不读原始 HTML / JSON / 二进制
- 纯数字、参考文献、空节点等**机械内容由脚本跳过**，不进模型

### 0.3 输出压缩
- 输出 >2KB 写文件，上下文只留路径和统计
- 中间结果用紧凑 JSON（`{"index": "值"}`），不写完整结构/调试信息
- 3+ 步批处理用 `execute_code`，重读/大段处理委托子代理（delegate_task）

### 0.4 交付
- 交付前检查：本任务有没有重复造轮子？有没有可以沉淀成技能脚本的步骤？

## 一、核心原则（全体系通用）

### 1. 事实零演绎
- **硬底线**：所有具体事实（人物、数字、时间、事件、原话）必须有来源
- 禁止编造：不脑补心理活动、不编对话、不虚构场景、不猜测未公开信息
- 直接引语必须加引号 + 标注来源（"某某说"、"据某报道"等）
- 来源不明的素材，宁可不写

### 2. 专业优先，在此基础上易懂
- 先把深度和专业性做足，再考虑表达方式的通俗性
- **"专业"的定义**：不是堆砌术语，而是有技术拆解、有行业背景、有逻辑推理
- 技术术语第一次出现要有简短解释（一两句话说清是什么）
- 分析要深入一层：不仅说"发生了什么"，还要说"为什么会这样"、"这意味着什么"
- 用类比和例子帮助理解，但类比不能误导
- 不因为怕读者看不懂就砍掉关键技术细节

### 2.5 写作质量底线（全体系通用）

**1. 段落完整**
每段围绕一个核心意思，有论点、有事实、有展开，2-5 句话说完，读者读完这一段知道你想说什么。

**2. 句子衔接**
正确使用标点符号，让句子之间逻辑关系清晰。

**3. 段落连贯**
段落之间有自然的逻辑衔接，层层递进、紧凑、有序。

**4. 节奏有变化**
段落长短错落，信息密度有起伏，论证方式根据素材选择合适的方式。

**5. 每篇必附质量说明和信息来源**
文末附附录：内容质量说明（事实准确性/断言强度/证据匹配度/反方视角/预测成分/适用范围）+ 信息来源（来源名称/标题/链接）。

### 3. 每个判断有推理链
- 所有重要结论都要有支撑（事实 + 逻辑）
- 不说空话、不喊口号
- 推理过程要可见：因为 A 且 B，所以 C
- 区分"事实陈述"和"观点判断"，观点判断要明确标示（"笔者认为"、"从这个角度看"）
- **断言强度 ≤ 证据强度**：强断言需要强证据，证据不够就降级表述（见下文"断言与证据匹配"）

### 3.1 断言与证据匹配（真实性红线）

**原则：从素材能推出多远的结论，就说多远。不越级。**

#### 证据强度分级
| 级别 | 定义 | 例子 |
|------|------|------|
| S | 同行评审 + 可复现 + 多方独立验证 | 顶会论文 + 多个团队复现 |
| A | 知名机构发布 + 具体数据 + 方法公开 | 大厂技术报告、HF 博客论文 |
| B | 单一来源 + 有具体数字 + 方法不透明 | 媒体报道、公司 PR |
| C | 传闻/匿名/分析师预测 | 未证实的消息 |

#### 断言强度分级
| 级别 | 定义 | 要求的证据级别 |
|------|------|---------------|
| 强 | "X 已经改变了 Y"、"X 打败了 Y"、"下半场开始" | S 或 A，且 ≥2 个独立来源 |
| 中 | "X 正在出现"、"X 指向 Y"、"X 值得关注" | A 或 B |
| 弱 | "X 是一个信号"、"X 可能意味着 Y" | B 即可 |

#### 标题三级匹配制
标题的断言级别不得超过内容的证据级别：
- **L1 事实级**：只陈述事实，不下判断 → 任何级别都能用
- **L2 趋势级**：说"正在发生""指向某个方向" → 需要至少 A 级证据 + 合理因果链
- **L3 判断级**：说"改变了""下半场""改写规则" → 需要 S 级 + 市场验证 + 多个案例

**判断方法**：写完标题问自己——"内容里的证据撑得住这个标题吗？"撑不住就降级。

#### 套话黑名单（直接替换，不用犹豫）
| 禁用 | 替换为 |
|------|--------|
| 颠覆认知 | 和直觉相反的是 |
| 很多人不知道 / 没人注意到 | 删掉 |
| 信号很明确 | 放在一起看，有一个共同的模式 |
| 下半场开始 / 新时代 | 这是一个值得注意的转向 |
| 改写规则 / 彻底改变 / 巨变 | 会带来具体的变化（然后列出来） |
| 革命 / 炸裂 / 史诗级 | 删掉 |
| 你还不知道就晚了 / 再不行动就 | 删掉（禁止制造焦虑） |

### 4. 论证主线
- 整篇文章要有一条贯穿始终的推理链，每个部分、每一段都在这条链上扮演明确角色（立论 / 论据 / 反方 / 收束 / 落地）
- 小标题是论点不是分类标签，读者看完每一节都应该离最终结论更近一步
- 写之前先搭论证骨架：核心论点 → 主要论据 → 反方观点 → 让步或反驳 → 最终结论。骨架顺了再动笔
- 没有论证角色的句子和段落，删掉

### 5. 必须有反方视角
- 任何重要话题都要呈现至少一个反对意见/风险/局限性
- 不做单面叙事
- 反方视角要认真对待（不是稻草人），要说出合理之处

### 6. 可溯源
- 关键事实要标注来源（报道名称、视频时间点、论文标题等）
- 读者应该能顺着来源找到原始材料
- 数据必须有出处，不能用"据说"、"有人说"

## 二、内容分层规则

所有内容都要区分以下三层，读者能看出来哪层是哪层：

| 层级 | 定义 | 标注方式 |
|------|------|----------|
| **原事实** | 直接来自来源材料的事实、原话、数据 | 直接陈述 + 引号/来源标注 |
| **背景知识** | 行业公知常识、历史背景、技术原理补充 | 用"【背景】"前缀，或单独段落 |
| **分析判断** | 基于事实的推理、解读、观点 | 用"从这个角度看"、"笔者认为"等明确标示 |

**比例底线**：原事实 ≥ 60%，扩充内容 ≤ 40%。

## 三、交付规范

1. **格式**：默认提供 Markdown 原文件 + HTML 页面
2. **HTML**：用 ai-content-imagery 技能生成
   - 头条版默认用 `plain`（朴素发布版）主题，方便复制粘贴到平台后台
   - 公众号/深度文默认用 `wechat-light` 主题（白底+微信绿，公众号编辑器兼容）
3. **文件命名**：`{主题名}-{平台名}-{日期}.{扩展名}`
   - 示例：`小模型逆袭-头条-20260825.html`、`小模型逆袭-公众号-20260825.md`
   - 日期格式：YYYYMMDD，无分隔符
   - 平台名：头条 / 公众号 / 小红书 / 核心稿
4. **交付方式**：单发 HTML 文件，不打包，不带默认 PNG
5. **飞书路径**：用相对路径发文件（lark-cli 要求）
6. **质量检查**：交付前必须过对应技能的质量检查清单 + 真实性自检清单

## 四、各技能的定位分工

| 技能 | 定位 | 输入 | 输出 |
|------|------|------|------|
| `ai-content-production` | 主入口 · 日常内容生产 · 一鱼三吃 | 素材选题 | 多平台内容（核心稿+头条+小红书+...） |
| `video-to-deep-blog` | 深度长文 · 视频字幕转写 | 字幕文件 | 4000-8000字专业深度长文 |
| `webpage-translation` | 网页翻译 · 英文博客中文化 | 网页 URL | 中文 HTML 单文件（内嵌图片） |
| `ai-content-imagery` | 视觉渲染 · HTML/封面/长图 | Markdown / 内容数据 | HTML / PNG |
| `ai-content-metrics` | 数据复盘 · 效果分析 | 发布数据 | 复盘报告 + 优化建议 |

```
素材 → [生产技能] → Markdown → [imagery] → HTML/图片
                           ↓
                    [metrics] ← 发布数据

网页翻译单独管线：
URL → [webpage-translation] → 中文 HTML（成品）
                            ↘  作为素材进入生产技能
```
