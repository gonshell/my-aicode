# 技术博客生产（Tech Blog Production）

> 本技能属于 ai-studio 内容生产体系。定位：**单技术主题深度调研 → 高质量公众号技术博客**。
> 与 ai-content-production 互补：它做资讯策展/日更/三平台分发，本技能做深度技术调研/按需/单平台深度输出。
> 共享资源：ai-content-imagery（HTML渲染）、文字质感提升清单、shared/RULES.md。

## 适用场景

- 一个新技术/新概念需要深度拆解并写成公众号文章
- 技术选型对比分析
- 技术原理深度解读
- 行业技术趋势盘点
- 有争议的技术话题分析

**不适用场景**：
- AI资讯日更/热点快评 → 走 ai-content-production
- 微头条/小红书图文 → 走 ai-content-production
- 纯事实型技术报告/白皮书 → 走 deep-research-report 技能

## 输入与输出

### 输入（用户提供）

| 参数 | 必需 | 默认值 | 说明 |
|------|------|--------|------|
| 技术主题 | 是 | — | 技术名词/事件/概念 |
| 骨架类型 | 否 | 自动判断 | 六类之一，见下 |
| 目标读者 | 否 | AI从业者/技术管理者 | 影响深度和解释密度 |
| 飞书归档 | 否 | false | 是否写入飞书文档 |

### 输出（默认交付）

1. **`{主题}-{类型}-{YYYYMMDD}.md`** — Markdown 原文
2. **`{主题}-{类型}-{YYYYMMDD}.html`** — 公众号格式 HTML（wechat-light 主题）
3. 文末附参考资料清单（≥5个来源，带链接）

### 可选附加

- 飞书文档归档（用户指定才做）
- PNG 长图（用户指定才做）

## 配置机制

优先级：**参数 > 环境变量 > 技能目录 config.json > 默认值**

配置文件：`~/.hermes/skills/ai-studio/tech-blog-production/config.json`

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `default_skeleton` | "拆解型" | 默认骨架类型 |
| `default_target_reader` | "AI从业者/技术管理者" | 目标读者 |
| `default_word_count` | "4000-6000" | 目标字数范围 |
| `default_html_theme` | "wechat-light" | HTML主题 |
| `references_min_count` | 5 | 最少来源数 |
| `search_rounds_max` | 3 | 最多检索轮次 |
| `feishu_archive_default` | false | 是否默认飞书归档 |

## 完整工作流（7步）

```
步骤1：主题确认与范围界定  （2min）
   ↓
步骤2：多轮定向检索  （5-15min）
   ↓
步骤3：选骨架 + 搭论证结构  （3min）
   ↓
步骤4：写作  （15-30min）
   ↓
步骤5：质量自检  （3min）
   ↓
步骤6：生成公众号 HTML  （1min）
   ↓
步骤7：交付  （1min）
```

预估总耗时：25–50分钟（取决于主题深度）

---

### 步骤1：主题确认与范围界定

**做什么**：明确这篇文章要回答的核心问题，划定范围边界。

**输出**：
- 核心问题：这篇文章要回答什么？
- 范围边界：写什么，不写什么
- 目标读者确认

**如果主题模糊**：做一次快速试探性检索，搞清楚这是什么领域的东西，再界定范围。不要上来就大检索。

---

### 步骤2：多轮定向检索

**核心原则**：检索是为了找素材，不是为了"多"。每一轮检索有明确目标。

**第一轮：概念确认**
- 查什么：这个技术是什么、谁提出的、官方出处
- 目标：建立基本共识，搞清楚术语和定义
- 关键词：技术名 + official / paper / technical report / 官方

**第二轮：技术细节**
- 查什么：原理、架构、参数、数据、对比
- 目标：挖到足够的"活料"——具体数字、具体公式、具体架构图描述
- 关键词：技术名 + architecture / principle / vs / benchmark / performance

**第三轮：背景与反方**（可选，素材够了就跳过）
- 查什么：历史背景、竞品对比、批评声音、局限性
- 目标：建立反方视角，避免一面倒
- 关键词：技术名 + limitation / challenge / vs 竞品 / criticism

**检索工具优先级**：
1. qwen-harness Web Search（主力，中文技术信息强）
2. web_extract（需要深挖某篇原文时）
3. searxng（补充）

**素材质量判断**：
- ✅ 官方技术报告/论文 → 第一优先级
- ✅ 权威技术媒体深度分析（Ars Technica / The Verge / 量子位深度等）
- ⚠️ 普通博客/知乎回答 → 参考用，不能当事实依据
- ❌ 二手转述/营销号 → 不用

---

### 步骤3：选骨架 + 搭论证结构

#### 3.1 六类骨架选型

根据素材形状和要回答的问题选骨架：

| # | 骨架类型 | 适用场景 | 你要回答的问题 | 难度 |
|---|---------|----------|-------------|------|
| 1 | **拆解型**（默认） | 新技术/新概念解析 | "这东西到底是什么、怎么工作、意味着什么？" | ★★☆ |
| 2 | **对比型** | 技术选型/方案对比 | "A和B哪个好？怎么选？" | ★★☆ |
| 3 | **教程型** | 实操指南/踩坑记录 | "怎么做到？有什么坑？" | ★☆☆ |
| 4 | **盘点型** | 一类技术/工具全景 | "现在有哪些玩家？格局怎样？" | ★★★ |
| 5 | **深潜型** | 技术原理深度拆解 | "底层原理到底是什么？" | ★★★ |
| 6 | **观点型** | 趋势判断/争议话题 | "我认为XX，为什么？" | ★★★ |

**默认选择**：如果用户没指定，素材是单个新技术 → 拆解型。

每类骨架的详细结构模板见 `references/tech-blog-skeletons.md`。

#### 3.2 搭论证骨架

选定骨架类型后，填论证五要素（这是文章的"脊梁骨"，不是目录）：

| 要素 | 作用 | 怎么填 |
|------|------|--------|
| **核心论点** | 文章要证明什么 | 你最想让读者记住的那个判断，一句话 |
| **核心论据** | 用什么证明 | 支撑论点的3-5个关键事实/数据/案例 |
| **反方视角** | 对方可能怎么反驳 | 最有力的反对意见是什么 |
| **让步** | 哪些地方你承认对方有理 | 你的论点的边界和局限 |
| **结论** | 最终判断 | 综合之后你站哪边、为什么 |

**检验方法**：把这五要素念一遍，如果逻辑通顺、论据能支撑论点，就可以动笔了。如果不通，说明要么论点太大、要么论据不够，回去调整。

---

### 步骤4：写作

#### 写作顺序

1. 先把骨架展开成目录（章节标题）
2. 从中间最难写的章节开始（技术原理部分），别从开头磨
3. 最后写开头和结尾

#### 技术博客写作规范

**在 ai-content-production 的通用规范基础上**，加技术博客特有的：

1. **原理准确性优先于通俗性**
   - 类比不能误导，技术细节不能为了好懂而失真
   - 如果准确和通俗冲突，先保证准确，然后再想办法用类比辅助理解

2. **关键概念必须定义**
   - 第一次出现的专业术语要给准确定义
   - 不能假设读者知道
   - 定义方式：一句话精确定义 + 通俗类比（如果有）

3. **数据必有来源**
   - 所有技术参数、性能数据、规模数据必须标注来源
   - 来源级别：官方论文/报告 > 官方文档 > 权威媒体 > 其他
   - 估算值必须明确标注"估算"

4. **类比必有边界**
   - 每个类比后面说明"这个类比不准确的地方在哪"
   - 防止读者被类比误导

5. **局限性必讲**
   - 技术的适用边界、已知缺陷、未解决问题必须说清楚
   - 不能只说好的，不说差的
   - 反方视角不是装饰，是真正有质量的对立观点

6. **术语统一**
   - 全文同一概念用同一术语，不随意换说法
   - 缩写第一次出现时写全称

#### 文字质感（共享 ai-content-production 规范）

- 段落是语义单元（2-5句/段）
- 句子长短交错，打破均匀节奏
- 砍掉80%的连接词和路标句
- 每篇至少一个明确的判断
- 标题服务于内容，不服务于结构
- 结尾落地，不喊口号

---

### 步骤5：质量自检

写完后过三遍检查：

**第一遍：技术严谨性**（见 `references/technical-accuracy-checklist.md`）
- [ ] 关键概念有明确定义
- [ ] 原理描述准确，没有为了通俗而失真
- [ ] 所有数据有来源标注
- [ ] 类比有边界说明
- [ ] 局限性/反方视角已覆盖
- [ ] 术语全文统一

**第二遍：真实性红线**（见 ai-studio/shared/RULES.md）
- [ ] 零演绎，所有事实有来源
- [ ] 标题断言级别 ≤ 证据级别（三级匹配制）
- [ ] 没有套话空话
- [ ] 参考资料≥5个，带链接

**第三遍：文字质感**
- [ ] 段落是语义单元，不是碎片化
- [ ] 节奏有变化，不是清一色长句或清一色短句
- [ ] 连接词砍到最少
- [ ] 有一个明确的判断
- [ ] 结尾落地

### 步骤6：生成公众号 HTML

调用 `ai-content-imagery` 的 `generate_article.py` 脚本：

```bash
python3 ~/.hermes/skills/ai-studio/ai-content-imagery/scripts/generate_article.py \
  input.md output.html \
  --title "文章标题" \
  --subtitle "副标题" \
  --theme wechat-light
```

**为什么默认 wechat-light**：
- 公众号编辑器对原生 table、CSS 渐变等支持差
- wechat-light 主题用 div 表格 + 内联样式优先
- 复制粘贴到公众号后台后样式保留率最高

---

### 步骤7：交付

**默认交付物**：
- Markdown 原文
- 公众号格式 HTML
- （飞书归档仅在用户指定时才做）

**交付格式**：先给链接/文件，再给结构概览（几章、多少字、核心内容）。

## 与其他技能的关系

```
ai-studio/
├── ai-content-production    ← 资讯策展/日更/三平台
├── tech-blog-production     ← 本技能：技术深度调研/按需/公众号深度
├── ai-content-imagery       ← 共享：HTML/图片渲染
├── ai-content-metrics       ← 共享：数据复盘
└── shared/                  ← 共享规则（RULES.md等）
```

**协作原则**：
- 不重复造轮子：HTML渲染用 imagery，写作规范共享 production 的
- 职责清晰：本技能只做"技术调研→技术博客"这一件事
- 触发不冲突：资讯类走 production，技术深度类走本技能

## Pitfalls

1. **检索不够深就动笔** → 强制至少两轮检索：第一轮确认概念，第二轮挖细节。素材不够就继续搜，不要硬写。
2. **类比过度简化** → 技术严谨性第4条：每个类比必须说明边界。准确比通俗重要。
3. **写成论文翻译** → 技术博客≠论文翻译。要有判断、有结构、有读者视角。问自己："读者看完这篇能得到什么？"
4. **堆术语不解释** → 第一次出现的专业术语必须给解释。目标读者是技术从业者，不是同领域研究者。
5. **只有一面之词** → 必须有反方视角/局限性章节。技术没有银弹，只说好的就是不专业。
6. **和 ai-content-production 职责混淆** → 触发词区分：资讯热点/日更/三平台 → production；技术深度调研/单篇深度 → 本技能。
7. **默认飞书归档** → 本技能默认不写飞书，只有用户明确要求才做。不要假设用户需要飞书。
8. **骨架选不对硬写** → 素材形状决定骨架类型。一个孤立事件别硬套盘点型，三个独立事件别硬套深潜型。
9. **边写边改浪费时间** → 骨架先搭顺了再动笔。骨架不对，写多少都得改。
