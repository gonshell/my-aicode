# Domain Glossary

## 企业知识库领域术语
- **知识库 (KB)**: 结构化存储企业知识的核心系统
- **知识条目 (Article)**: 单条知识内容
- **分类 (Category)**: 知识的层级分类
- **标签 (Tag)**: 知识的扁平标记
- **向量索引 (Vector Index)**: 语义检索的底层结构
- **问答 (QA)**: 用户提问 → 知识库回答的交互

🎯 核心问题回答

Q: 需要建立 Git 来管理过程文档么？

A: 必须建立，且分区管理：

内容 是否入 Git 原因
docs/agents/* ✅ 必须 技能配置，所有协作方共享
docs/product/prd/* ✅ 必须 to-spec 输出的正式规格，版本化管理
docs/product/domain-model/* ✅ 必须 领域模型是核心资产
docs/product/research/* ✅ 必须 调研结论需要追溯
docs/engineering/adr/* ✅ 必须 架构决策必须可追溯
.scratch/* ❌ 不提交 to-tickets 的临时工单，动态变化
对话历史 ❌ 不提交 留在 Agent session 中，重要结论提炼后写入文档
原型代码 ⚠️ 独立分支 验证后可合并或删除

推荐执行路径

setup-matt-pocock-skills ↓ domain-modeling ↓ grill-me → grilling → (grill-with-docs) ↓ to-spec ↓ codebase-design ↓ to-tickets ── (超大规模时) → wayfinder ↓ ↓ implement research + prototype ↓ code-review ↓ handoff

📌 关键原则

  • 文档即代码：所有正式产出（PRD、领域模型、ADR）都走 Git 提交流程，和代码一样 review
  • 临时文件隔离：.scratch/ 下的动态工单不提交，避免 Git 历史被细碎修改污染
  • 里程碑打 tag：to-spec 完成打 prd-v1 tag，架构设计完成打 arch-v1 tag
  • 决策可追溯：每个重要决策写入 ADR，包含背景、选项、决定、理由
  • 垂直切片而非水平分层：每张工单贯穿 schema → API → UI → 测试全链路
  • 一次只问一个问题：避免多问题同时抛出造成困惑
  • 决策地图而非任务清单：wayfinder 解决的是不确定性，不是执行
  • 双轴评审分离：规范正确 ≠ 需求正确，两者独立报告
