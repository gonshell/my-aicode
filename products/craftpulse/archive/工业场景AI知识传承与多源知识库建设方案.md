# 匠脉 (CraftPulse) — 工业场景AI知识传承与多源知识库建设方案

## ——基于Skills驱动架构的完整实施指南——


## 一、方案背景与核心目标

### 1.1 要解决的四大核心问题

| 序号 | 核心问题 | 具体描述 |
|:---:|:---|:---|
| **1** | 老专家隐性知识传承 | 老师傅头脑中的实操经验、故障直觉、判断逻辑，长期碎片化存在，面临失传风险，需系统化显性沉淀 |
| **2** | 多源文本知识整合 | 企业拥有专业技术参考书、国家标准/行业规范、内部规章制度、历史案例报告等大量文本，分散在不同介质，无法统一检索调用 |
| **3** | 统一格式标准化输出 | 所有知识产出物必须统一为Markdown格式，并附带标准化标注/元数据，同时满足人工阅读与机器解析双重需求 |
| **4** | 多平台智能化消费 | 知识库须能够直接对接大模型RAG检索增强生成、GraphRAG图关系推理、Obsidian知识可视化、Dify智能应用编排等平台 |

### 1.2 方案设计理念

本方案借鉴 [mattpocock/skills](https://github.com/mattpocock/skills/tree/main) 项目架构哲学，将知识管理的每个环节封装为 **AI Agent可加载执行的标准化技能（Skill）** ，每个技能通过 `SKILL.md` 文件定义：

- **小、可适配、可组合**：每个技能只做一件事，技能之间通过标准化的输入/输出衔接
- **基于Prompt驱动**：技能的核心是结构化指令集，通过精准的Prompt约束AI行为，而非编写代码
- **状态无关、上下文在文件中**：所有配置、术语、待办事项等状态信息，全部记录在项目目录的Markdown文件中，不依赖外部数据库
- **人机共享统一语言**：通过 `CONTEXT.md` 定义项目专属术语，确保人与AI对同一概念的理解完全一致

## 三、统一规范体系（所有技能必须遵守的刚性标准）

### 3.1 知识文件元数据强制Schema

每个知识条目的 `.md` 文件头部必须包含以下 **11个核心YAML字段**，缺一不可：

```yaml
---
# ========== 必填核心字段 ==========
knowledge_id: "KB-20260128-001"         # 全局唯一ID，格式：KB-YYYYMMDD-序号
source_type: "expert"                  # 枚举: book | expert | regulation | case
title: "离心机振动异常处理经验"        # 知识标题
author: "张工"                          # 作者/来源人
equipment_scope:                       # 适用设备清单（至少1个）
  - "MCO-101"
  - "MCO-102"
knowledge_tags:                        # 标签（至少3个）
  - "振动"
  - "油温"
  - "频谱分析"

# ========== 版本与状态 ==========
version: "v1.0"                        # 语义化版本号
status: "active"                       # 枚举: draft | active | superseded | deprecated
effective_date: "2026-01-28"           # 生效日期
expiry_date: "2027-01-28"              # 过期日期（专家经验默认1年，规程默认3年）

# ========== 置信度与溯源 ==========
confidence_score: 0.95                 # 0-1区间，计算规则见第3.2节
source_references:                     # 溯源引用（至少1个）
  - "张工访谈记录_20260128_第3段"
  - "运行日志_2025-06-15"

# ========== 治理追踪 ==========
last_reviewed: "2026-01-28"            # 最后复核日期
change_log: "初版创建"                  # 变更说明
---
```

### 3.2 置信度（confidence_score）计算规则

| 知识来源类型 | 基础分 | 修正项（累加） | 封顶值 |
|:---|:---:|:---|:---:|
| **专家经验** | 0.70 | ① 经另一位专家交叉验证 → +0.15<br>② 有运行数据佐证 → +0.10<br>③ 与历史案例一致 → +0.05 | 0.98 |
| **专业书/标准** | 0.85 | ① 为最新版本 → +0.10<br>② 已在本厂实际应用验证 → +0.05 | 0.99 |
| **规章制度** | 0.80 | ① 为最新发布版本 → +0.10<br>② 有合规部门审批 → +0.05 | 0.98 |
| **融合知识** | 0.75 | ① 多源完全一致 → +0.20<br>② 有冲突但已裁决 → +0.10<br>③ 经总工审批 → +0.05 | 0.98 |

AI产出每条知识时，须按此规则计算并在YAML中注明计算依据（通过 `source_references` 字段体现）。

### 3.3 GraphRAG 实体与关系枚举（Schema）

所有知识文件内嵌的 ````json` 代码块中，实体和关系必须严格遵循以下枚举：

**实体类型（Entity Types）**：
```
Equipment | Component | Parameter | Material | Procedure | Fault | Personnel
```

**关系类型（Relation Types）**：
```
causes | solves | indicates | requires | has_parameter | located_in | applies_to | supersedes
```

**正确示例**：
```json
{
  "entities": [
    {"id": "MCO-101", "type": "Equipment", "name": "离心压缩机"},
    {"id": "VIB-01", "type": "Parameter", "name": "轴振动振幅"}
  ],
  "relations": [
    {"head": "MCO-101", "relation": "has_parameter", "tail": "VIB-01"},
    {"head": "高振幅", "relation": "causes", "tail": "轴承损坏"}
  ]
}
```

**错误示例（会被CI拦截）**：
```json
{
  "entities": [
    {"id": "MCO-101", "type": "Machine"}  // 不在枚举内，非法
  ]
}
```

## 四、各技能详细定义与完整执行路径

### 技能1：知识库初始化（`/setup-industry-kb`）

**技能定位**：企业首次部署知识库时的启动技能，定义术语、分类、目录结构与全局规则。**必须先执行，无任何依赖。**

**SKILL.md 核心指令**：

```markdown
---
name: setup-industry-kb
description: 初始化工业知识库的目录结构、术语表、标签体系和全局配置
---

# 触发条件
当用户说以下任一指令时激活：
- "/setup-industry-kb"
- "初始化知识库"
- "创建知识库配置"

# 执行流程

## Step 1: 读取系统上下文
- 检查当前工作目录是否存在 CONTEXT.md
- 若存在，则提示用户"知识库已初始化，如需重新配置请指定 --force"

## Step 2: 向用户收集配置信息（清单式提问）
按顺序依次提问，每次只问一个问题，等待用户回答后再问下一个：

**Q1**：请列出本企业涉及的核心设备类型（用逗号分隔，如：离心压缩机、齿轮箱、冷却塔）
**Q2**：请列出常用的故障分类（用逗号分隔，如：机械故障、电气故障、工艺故障）
**Q3**：知识库文件将存放在哪个本地目录？（如：C:\industrial-kb\）
**Q4**：是否同步至Git仓库？若是，请提供仓库地址。

## Step 3: 生成配置文件
根据用户回答，生成以下文件：

### 3.1 生成 CONTEXT.md
包含：
- 术语表：将用户Q1的回答整理为"口语 ↔ 标准术语"映射表
- GraphRAG Schema：写入第3.3节定义的实体/关系枚举
- 置信度规则：写入第3.2节定义的计算规则

### 3.2 生成 docs/agents/issue-tracker.md
记录：
- 知识条目存储位置（用户Q3的回答）
- 待办事项跟踪方式（用户Q4的回答）
- 初始状态：无待办

### 3.3 生成 docs/agents/labels.md
记录：
- 设备标签：用户Q1的回答
- 故障标签：用户Q2的回答

### 3.4 创建目录骨架
按第3.4节目录结构，创建所有子目录。

## Step 4: 产出成果并汇报
生成 _index.md，写入技能依赖关系图，并向用户汇报：
*"匠脉 (CraftPulse) 初始化完成。配置文件见 CONTEXT.md，目录结构已创建。您可以开始执行知识捕获技能：/ingest-technical-book、/capture-expertise 或 /to-spec。"*

# 约束条件
- 禁止跳过任何提问步骤
- 禁止在 Q1-Q4 未完成时创建目录
- CONTEXT.md 中的术语表必须包含"口语→标准术语"双向映射
```

### 技能2：专业技术参考书知识捕获（`/ingest-technical-book`）

**技能定位**：处理PDF/Word格式的专业技术参考书（如《机械设计手册》《离心压缩机原理》等），提取理论公式、设计参数、原理说明，转化为结构化知识条目。与技能3、4可并行执行。

**SKILL.md 核心指令**：

```markdown
---
name: ingest-technical-book
description: 从专业技术参考书PDF中提取理论知识、公式、设计参数，转化为结构化知识
---

# 触发条件
当用户说以下指令时激活：
- "/ingest-technical-book --file=<文件路径>"
- "解析这本技术书"

# 前置依赖
必须已完成 /setup-industry-kb（CONTEXT.md 必须存在）

# 执行流程

## Step 1: 验证输入
- 检查 --file 参数指定的文件是否存在
- 若不存在，提示用户提供正确的文件路径
- 检查文件扩展名（仅支持 .pdf、.docx、.txt）
- 若为 .pdf，进入 Step 2；若为 .docx/.txt，直接进入 Step 3

## Step 2: PDF预处理（识别文档类型）
- 使用 pdfminer/pypdf 检测PDF是否含文本层
- **若含文本层**：直接进入 Step 3
- **若无文本层（扫描版）** ：提示用户选择处理方式：
  A. "请提供该书的Word/文本电子版（推荐）"
  B. "使用OCR识别（需安装Tesseract，准确率约85%）"
  C. "仅手动录入关键章节（我将为您提供录入模板）"
- 根据用户选择进入相应分支

## Step 3: 扫描目录与提问
- 读取PDF目录/文档结构，识别章节列表
- 向用户提问：
  *"本书共识别到 [N] 章。请选择与本企业 [已读取CONTEXT.md中的设备列表] 直接相关的章节（可多选）："*
  列出所有章节名称供用户选择。

## Step 4: 逐章深度提取
对用户选中的每一章，依次执行以下操作：

### 4.1 提取理论公式
- 识别文档中的数学公式（文本版识别 LaTeX 格式，扫描版通过OCR+人工复核）
- 格式化为 LaTeX 代码块：```math ... ```
- 在公式下方添加"变量说明"表格

### 4.2 提取设计阈值参数
- 识别数值型参数（如尺寸公差、温度限值、压力范围）
- 存入 YAML 代码块，包含：参数名、最小值、最大值、单位、适用条件

### 4.3 提取原理说明
- 保留原文核心论述（100-300字），作为"人工解读"正文
- 标注原文页码（溯源）

### 4.4 提取图表
- 记录图号、标题
- 在正文中保留图表描述
- 若为扫描版，在元数据中标记 `image_reference: "图X-X见原书第P页"`

### 4.5 生成"理论 vs 本厂实际"差异对照
- 将提取的参数与本厂实际运行参数（如有）对比
- 生成差异清单表格

## Step 5: 产出标准化Markdown
文件路径：`knowledge/books/[书名]/v1.0/提取结果.md`

必须包含：
- YAML Frontmatter（按第3.1节Schema）
- 章节结构与人工阅读正文
- 公式（LaTeX代码块）
- 参数（YAML代码块）
- 差异对照表
- JSON代码块（实体与关系，按第3.3节枚举）

## Step 6: 汇报并标记待办
- 向用户汇报提取统计（共提取X条参数、Y条公式、Z条原理）
- 在 issue-tracker.md 中记录："请人工复核第X页图X-X的标注是否清晰"

# 约束条件
- 禁止在用户未确认章节选择时进行深度提取
- 禁止将扫描版PDF直接解析（必须先让用户选择处理方式）
- 所有数值参数必须标注单位
- 置信度按第3.2节"专业书/标准"规则计算
```

**完整执行路径示例**：

| 步骤 | 角色 | 动作 | 内容/示例 |
|:---|:---|:---|:---|

### 技能3：专家隐性知识捕获（`/capture-expertise`）

**技能定位**：通过结构化访谈，将老专家的隐性经验（故障直觉、操作诀窍、判断逻辑）转化为可复用的知识条目。与技能2、4可并行执行。

**SKILL.md 核心指令**：

```markdown
---
name: capture-expertise
description: 通过结构化访谈捕获专家隐性经验，转化为标准化知识条目
---

# 触发条件
当用户说以下指令时激活：
- "/capture-expertise --expert=<姓名> --topic=<主题>"
- "访谈张工关于[主题]的经验"

# 前置依赖
必须已完成 /setup-industry-kb（CONTEXT.md 必须存在）

# 执行流程

## Step 1: 加载上下文
- 读取 CONTEXT.md，获取统一术语表
- 读取 docs/agents/labels.md，获取标签体系

## Step 2: 确认访谈范围和目标
向用户提问：
*"即将访谈 [专家名]，主题为 [主题]。预计需要30-45分钟。请问是否需要我将访谈提纲发给您提前预览？"*

## Step 3: 结构化访谈（核心环节）
严格按照以下问题清单推进，穷尽所有决策分支：

**第一轮（场景还原）**：
- Q1："请回想最近一次您印象深刻的 [主题] 事件，当时设备运行参数（转速、负荷、温度）是多少？"
- Q2："您最先注意到的异常信号是什么？"

**第二轮（诊断推理）**：
- Q3："您当时的第一个判断是什么？为什么？"
- Q4："您采取的第一步操作是什么？为什么选择这个操作？"
- Q5："如果情况A发生，您会怎么办？如果情况B发生呢？"（穷尽分支）

**第三轮（边界条件）**：
- Q6："什么情况下您会改变判断？"
- Q7："这个经验有没有例外？什么时候不适用？"

**第四轮（量化确认）**：
- Q8："请给出您认为关键的数值阈值（如：温度超过多少要警惕）"

## Step 4: 结构化整理（AI内部处理）
- 将口语转化为"条件→判断→行动"逻辑链
- 提取关键参数阈值（量化）
- 生成决策树草稿（Mermaid格式）
- 标注风险等级（高/中/低）

## Step 5: 回读确认（关键质量控制）
将整理结果向专家复述：
*"[专家名]，我总结一下：当[条件A]且[条件B]时，您的判断是[判断C]，优先操作是[行动D]。只有在[例外条件E]时才改变策略。对吗？"*
- 专家确认 → 进入 Step 6
- 专家修正 → 根据修正更新，重新进入 Step 5

## Step 6: 产出标准化Markdown
文件路径：`knowledge/experts/[专家名]/v1.0/[主题]_经验.md`

必须包含：
- YAML Frontmatter（按第3.1节Schema，confidence_score按第3.2节"专家经验"规则计算）
- 决策树（Mermaid代码块）
- 结构化经验条目（JSON代码块，每条包含 condition/action/rationale/risk_level/exception）
- 实体与关系（JSON代码块，按第3.3节枚举）

## Step 7: 提交融合待办
在 issue-tracker.md 中记录：
*"待办：将[专家名]的[主题]经验与国标/现有知识做冲突检测"*

# 约束条件
- 禁止在回读确认环节跳过（这是防"经验遗漏"的关键闸门）
- 禁止使用非 CONTEXT.md 中定义的术语
- 每条经验必须有明确的"例外条件"
```


### 技能4：规章制度/标准文档转化（`/to-spec`）

**技能定位**：将企业内部的规章制度、操作规程、国家标准等规范性文档，转化为机器可检索的结构化知识。与技能2、3可并行执行。

**SKILL.md 核心指令**：

```markdown
---
name: to-spec
description: 将规章制度/标准文档转化为结构化规范知识
---

# 触发条件
当用户说以下指令时激活：
- "/to-spec --file=<文件路径>"
- "转化这份规程为标准知识"

# 前置依赖
必须已完成 /setup-industry-kb（CONTEXT.md 必须存在）

# 执行流程

## Step 1: 验证输入
- 检查文件是否存在
- 支持格式：.docx、.txt、.pdf（带文本层）

## Step 2: 解析文档结构
- 提取章节、条款编号
- 识别强制关键词："必须"、"禁止"、"不得" → 标记 is_mandatory: true
- 识别建议关键词："宜"、"可"、"建议" → 标记 is_mandatory: false

## Step 3: 结构化拆解
- 将每一条"规定"抽取为独立条目
- 提取定量指标（数值+单位）→ 存入 YAML
- 提取执行条件（"当...时"）→ 存入 YAML 的 condition 字段

## Step 4: 冲突检测（自动比对已有知识库）
- 搜索 master/ 目录中相同设备/主题的已有条目
- 若存在冲突（如换油周期新旧版本不同），向用户汇报：
  *"发现冲突：[旧条目]与[新条目]对[主题]的规定不一致。请裁决：1)以新为准 2)保留旧 3)合并"*

## Step 5: 根据用户裁决更新
- 以新为准 → 旧条目标记 status: superseded
- 保留旧 → 新条目标记 status: draft，备注"待进一步核实"
- 合并 → 生成融合条目，注明"融合版本"

## Step 6: 产出标准化Markdown
文件路径：`knowledge/regulations/[规程名]/[版本号]/结构化.md`

必须包含：
- YAML Frontmatter（按第3.1节Schema，is_mandatory 字段为布尔值）
- 关键指标（YAML代码块）
- 执行条件（JSON代码块）
- 版本变更记录（表格）

## Step 7: 更新治理台账
在 governance/版本变更日志.md 中追加记录。
```

| 步骤 | 角色 | 动作 | 示例 |

| **1** | 用户 | 发起指令 | `@agent /to-spec --file="D:\docs\润滑油管理规程_v3.0.docx"` |
| **2** | AI | 解析文档 | 提取：油品牌号ISO VG 46、换油周期4000h、水分<0.05% |
| **3** | AI | 结构化拆解 | 每条规定独立成条目，标记 is_mandatory |
| **4** | AI | 冲突检测 | 检索 master/ 中发现旧版：换油周期3000h → 冲突 |

| **6** | 用户 | 裁决 | *"以新版4000h为准"* |
| **7** | AI | 产出 | 保存至 `knowledge/regulations/润滑油管理规程/v3.0/结构化.md`，旧版标记 superseded |
