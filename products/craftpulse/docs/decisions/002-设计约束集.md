# ADR-002：设计约束集（5条硬约束）

- **状态**：已接受（2026-08-01）
- **影响范围**：所有后续设计必须满足的边界条件

## 背景

方案需要有"顶层原则"来约束后续所有设计，防止执行走形。最初用词"宪法"，后被用户指出大词小用、过度类比，改为"设计约束集"——不是法律，是工程上的硬约束。

## 候选方案

1. 原则声明式（"我们应当重视质量"）——软性，无约束力
2. 硬约束集（不满足即打回）——强制，可执行
3. 不设原则，随设计自然演进——无纪律

## 权衡

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| 软原则 | 灵活 | 执行时会被绕过，等于没有 |
| 硬约束 | 可执行、防走形 | 可能限制创新，需定期review |
| 无原则 | 自由 | 设计会漂移，不可控 |

## 决定

采用**硬约束集**，共5条：

1. **约束1**：所有输入必须是结构化表单，不接受自由文本（知识质量可控）
2. **约束2**：可解释性优先于准确率（所有回答必须可溯源）
3. **约束3**：负面知识与正面知识同等重要（错误教训）
4. **约束4**：先帮专家减负，再谈知识萃取（专家配合度是生死线）
5. **约束5**：最终决策权永远在人（人机责任边界）

违反约束的设计方案直接打回重做。

## 理由

1. 5条约束对应5个被验证过的致命失败点（质量/信任/只学成功经验/专家不配合/责任风险）
2. 每条都有明确的可验证性（违反即打回），不是口号
3. 用户偏好务实、反对装饰，硬约束符合"直接给结果"的风格

## 后果

- 后续所有章节（知识表示/生产端/消费端/治理）都以5条约束为检查标准
- 约束需要定期review：当出现无法满足约束的合理场景时，修改约束而非绕过
